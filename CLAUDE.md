## Automated tests

`packages/engine-core/test/` (vitest, run via `pnpm --filter engine-core test`). Real SQLite (in-memory, via `test/helpers/testContext.ts`, which mirrors `engine-cli`'s `buildContext()`) and real temp directories (`test/helpers/tempDir.ts`) throughout — no mocking of the DB or filesystem. What's covered:

- **`retention/applyRetention.spec.ts`** — the highest-value suite: count-based, days-based, and combined-policy pruning; the two hard invariants (never delete without a later real backup, never go to zero); and dedicated regression tests for the two real bugs found while building retention (duplicate deletion records on repeated passes; no-op Success runs defeating the survivor floor — see the "Retention" section above).
- **`orchestrator/runBackupTask.spec.ts`** — the core pipeline (success, checksum fallback, `NoNewDumpAvailableError` handling, validation/empty-file failure, the app-level concurrency lock, stale-run recovery, orphaned `.part` cleanup, retention wiring) using a fake `BackupStrategyExecutor` injected via `RunBackupTaskDeps.resolveExecutorOverride` — a seam that exists **only** for this purpose; production code never sets it. Real transports/SSH/SFTP/DB connections are deliberately not exercised here (that's what the manual end-to-end testing against real local targets, described throughout this file, is for) — this suite is about the orchestrator's own logic, strategy-agnostic.
- **`transports/hostKeyVerification.spec.ts`**, **`transports/outputPathTemplate.spec.ts`**, **`validators/genericValidator.spec.ts`**, **`validators/mysqlDumpValidator.spec.ts`**, **`db/repositories/tasksRepo.spec.ts`** — smaller focused suites for host-key trust logic, the date-token template resolver, minimum-bar file validation, mysqldump/mariadb-dump's header/completion-footer structural check, and the strategy/transport/database-connection type invariants.
- **`config/exportImportConfig.spec.ts`** — export/import round-tripping, the name-collision failure path, and a hand-built malformed export (a task referencing a transport name that doesn't exist) to confirm per-item errors don't abort the rest of the client's import.

- **`databaseConnections/testDirectDumpCompatibility.spec.ts`** — every `toolCompatibility` branch (`registered`/`default-unverified`/`missing`) of the direct_dump pre-flight compatibility gate, via a `testConnectionOverride` injection seam (mirrors `RunBackupTaskDeps.resolveExecutorOverride`) so the connection+version step can be faked without a live DB server, with real temp files backing the "does the resolved tool path actually exist on disk" checks — including the `'registered'` branch for all three engines (postgres/mysql/mariadb).
- **`databaseConnections/mysqlToolRegistry.spec.ts`**, **`mariaDbToolRegistry.spec.ts`** — the mysqldump/mariadb-dump equivalents of `postgresToolRegistry.spec.ts`: their major.minor version-extraction edge cases (including MariaDB's `"-MariaDB"` suffix) and register/resolve/unregister round-tripping.

## What this app does

A local, internal, "extremely reliable" tool that centralizes database backups across multiple clients/servers. Core pipeline:

**connect to servers → fetch DB backups → store locally → validate → apply retention → show status clearly.**

It is explicitly **not** responsible for server administration or deploys. Scope is deliberately narrow — do not add these until asked (they're called out in the spec as out of scope for v1): file/upload backups, S3, FTP, Google Drive, full automatic restore, VPS administration, general server monitoring, external notifications, multi-user support, cloud sync, mobile app. Adapters should still be designed so these can be added later without rewriting the engine — but don't pre-build them.

## Mandated development approach (per project.md "Primera etapa")

The spec explicitly says: **do not build the whole app at once**, and the user wants to be **contradicted** when a technical decision in the spec doesn't hold up, not just agreed with. This governed the architecture phase (already done — see "Architecture" below) and still governs what comes next: **no feature beyond the currently-agreed increment without explicitly checking in first.** All three backup strategies, retention, an automated test suite for `engine-core`, connection testing, config export/import, and Task Scheduler registration are done; don't start on the GUI without asking (or on packaging) — each is a deliberate, separately-agreed increment, not a natural continuation to pick up unprompted. (This has held in practice across every increment so far — architecture, `fetch_existing`, `remote_dump`, `direct_dump`, retention, automated tests, connection testing + config export/import, Task Scheduler registration — each chosen via an explicit question or explicit request from the user before starting.)

## Distribution constraints (non-negotiable, shape the architecture)

The end product must be a distributable Windows executable/installer for non-technical daily use:

- Produces a `.exe` and preferably a Windows installer.
- Must **not** require Node.js, npm, Rust, or any dev tooling on the target machine.
- Launches from Start Menu / shortcut like a normal app.
- Config, SQLite DB, and logs persist under AppData or a configurable directory — **never inside the install folder** (so updates don't wipe them).
- Must support future app updates without losing configuration or history.
- The backup engine must be able to run **unattended via Windows Task Scheduler even when the GUI is closed** — avoid designing this as "always keep our own background process running" if Task Scheduler integration can do it.
- Packaging must bundle or correctly resolve whatever is needed to validate dumps (e.g. `pg_restore`) — do not assume PostgreSQL is installed globally on the target machine.

## Architecture: three separate concepts, not two

The spec originally framed this as just "connections" (SFTP/SSH), but the implemented model deliberately separates three concerns so a third strategy can be added later without reshaping the schema or the orchestrator:

- **Backup strategy** (`backup_tasks.strategy`, `BackupStrategyKind` in `engine-core/src/types.ts`): `fetch_existing` | `remote_dump` | `direct_dump`. Decides the overall pipeline shape. The orchestrator (`engine-core/src/orchestrator/runBackupTask.ts`) depends only on the `BackupStrategyExecutor` interface (`engine-core/src/strategies/types.ts`), never on a transport or DB-connection type directly.
- **Transport** (`transports` table, `engine-core/src/transports/`): `sftp` | `ssh` | `ftp` (ftp added 2026-08-25 — see "Backlog" below). How bytes move between a remote host and this PC. Used only by `fetch_existing` (sftp or ftp) and `remote_dump` (ssh).
- **Database connection** (`database_connections` table, `engine-core/src/databaseConnections/types.ts`): real DB credentials (engine, host, port, database, username, `password_secret_ref`). Used only by `direct_dump`. `fetch_existing`/`remote_dump` deliberately never need DB credentials.

Status of each strategy:

- **`fetch_existing` — implemented** (`strategies/fetchExistingExecutor.ts`, uses `transports/sftpAdapter.ts` or, since 2026-08-25, `transports/ftpAdapter.ts` — dispatched by the transport's own type): SFTP or FTP. Connect → list remote files → diff against `Success` runs by filename+size (not remote mtime — see below) → download newest candidate, hashing incrementally while streaming → return a `ProducedDump`. When nothing new is found it throws `NoNewDumpAvailableError`, which the orchestrator treats as a successful no-op run, not a `Failed` one — never surface "already up to date" as an error. Every invocation of the *next* strategy legitimately produces a fresh file, so this "already downloaded" concept is specific to `fetch_existing`.
- **`remote_dump` — implemented** (`strategies/remoteDumpExecutor.ts`, uses `transports/sshAdapter.ts` via raw `ssh2` — not `ssh2-sftp-client`, because it needs both `.exec()` and `.sftp()` on one connection): connect → run `transports.remote_command` → non-zero exit code fails the run → resolve the expected file path via `transports.remote_output_path_template` (supports a `{date:YYYYMMDD_HHmm}`-style token, resolved in `transports/outputPathTemplate.ts` — deliberately minimal, no heuristic "find the newest file" detection per the architecture plan's risk list) → download, hashing incrementally → if `transports.remote_cleanup` is set, delete the remote file **only after** a non-empty download succeeds (matches the spec's own step ordering: verify transfer, then optionally clean up). Gotcha already hit and fixed: `ssh2`'s raw `Client` is a plain `EventEmitter` — an unhandled `'error'` event (e.g. `ECONNRESET` after a rejected host key) crashes the whole process unless a permanent no-op listener is attached (see the comment in `sshAdapter.ts`); `ssh2-sftp-client` avoids this itself via a constructor `error` callback, which `sftpAdapter.ts` also sets.

## Security requirements

- Never store SSH private keys inside SQLite — store paths/references only.
- Never store passwords in plaintext; secrets are DPAPI-encrypted at rest — see "Secrets storage" below for what that means today (it changed once, deliberately, from the original plan).
- Never log credentials.
- Validate SSH host fingerprints; don't silently accept unknown hosts — support registering/confirming known hosts.
- Principle of least privilege: a backup user should not need root/admin on the remote server.

## Secrets storage

**Migrated 2026-08-24** from Windows Credential Manager (`@napi-rs/keyring`, CurrentUser-scope DPAPI under the hood) to a `secrets` table in this app's own SQLite database, encrypted with **LocalMachine-scope DPAPI** via `@primno/dpapi` (`secrets/machineDpapiStore.ts`, `MachineDpapiSecretStore`) — a real, user-initiated architecture change, not a bug fix, triggered by hands-on pain registering a real Windows Scheduled Task (see "Scheduler" below).

- **Why**: Credential Manager's CurrentUser-scope DPAPI meant only the specific Windows account that saved a secret could ever decrypt it again — which meant a Scheduled Task had to run *as that interactive user*, which meant `scheduler:install` needed that user's real Windows account password. The user hit this directly (a genuinely wrong-looking "usuario o contraseña incorrectos" error from `schtasks.exe` that turned out to be a PowerShell double-quote/`$`-interpolation issue, not a wrong password) and asked how other backup software avoids this. Answer, researched and confirmed: professional tools mostly run as a Windows Service (not a per-task Scheduled Task) and use either LocalMachine-scope DPAPI or their own master-password-derived key, precisely to decouple "can decrypt this secret" from "which specific human is logged in." LocalMachine-scope DPAPI was the smaller of the two changes and reused this app's existing `SecretStore` interface unchanged, so that's what got built.
- **What changed structurally**: `secrets` table added (`db/migrations/0003_add_secrets_table.sql` — `ref TEXT PRIMARY KEY, ciphertext BLOB`). `MachineDpapiSecretStore` implements the exact same `SecretStore` interface (`get`/`set`/`delete`) `WindowsCredentialManagerStore` did, so every caller (transports, database connections) needed zero changes. `@napi-rs/keyring` dependency removed entirely — nothing else used it.
- **What this unblocked**: `scheduler:install` now registers the task's Principal as SYSTEM (well-known SID `S-1-5-18`, no `LogonType`/password at all — see "Scheduler") since LocalMachine-scope DPAPI is decryptable by *any* account on the machine, SYSTEM included. This is the real payoff: a client install can now register scheduled backups with **zero password prompt**, which the original interactive-user design could never have offered a non-technical user cleanly.
- **A second, necessary fix this forced**: `paths.appDataDir()` (the SQLite DB + logs location) resolved via `%APPDATA%`, which is *per-user* — a SYSTEM-run process has its own, different, empty `%APPDATA%`, so it would never have found the real database at all. Moved to `%PROGRAMDATA%` instead (`C:\ProgramData\CodebiusBackupManager\`), Windows' own documented location for machine-wide data independent of which account is running — this would have silently broken every scheduled run otherwise, SYSTEM or not. `defaultBackupsRootDir()` (the UI's suggested-default new-client folder) moved the same way, for the same underlying reason plus a second one: a backup folder living inside a specific user's profile is exactly the kind of path a SYSTEM-run process might not have ACL access to, so the suggested default no longer points there at all.
- **SSH private keys now get copied into this app's own storage at creation time, not just at config-import time.** `transports/copyPrivateKey.ts` (`copyPrivateKeyIntoAppStorage`) — called from `transport:create-sftp`/`-ssh`/`:update` and their `serve` HTTP equivalents, right before the repo call — copies whatever file the user pointed at into `paths.keysDir()` (`%PROGRAMDATA%\CodebiusBackupManager\keys\<uuid>.key`, the same directory `config:import`'s restored keys already used — that helper's directory function was renamed `paths.importedKeysDir()` → `paths.keysDir()` to reflect it's no longer import-only) and stores *that* path on the transport. Same reasoning as the ProgramData move: a key file sitting wherever the user originally put it (their Downloads folder, another account's profile) isn't guaranteed readable by SYSTEM or guaranteed to still exist later; owning a copy sidesteps both problems.
- **Verified for real, not just unit-tested**: created a real transport with a real key file and a real passphrase through the actual running HTTP API, confirmed the key was copied with byte-identical content, confirmed the `secrets` table held real ciphertext (not plaintext) at the expected size, and confirmed `MachineDpapiSecretStore.get()` decrypted it back to the exact original passphrase — all against this machine's real DPAPI, not a fake. 145 vitest tests now pass (`machineDpapiStore.spec.ts` — 6 tests using real DPAPI calls, self-skips on non-Windows via `isPlatformSupported`; `copyPrivateKey.spec.ts` — 3 tests with real temp files).
- **`redactPassword`/the PIN-vs-password error hint built earlier the same day are now dead code, deleted rather than kept "just in case"**: there is no password anywhere in the scheduler flow anymore, so nothing to redact and no wrong-credentials error mode to hint about — the problem was eliminated at the root instead of just getting a better error message for it.

## Local storage layout

Conceptual path: `Backups/{cliente}/{database}/{YYYY}/{MM}/`, e.g. `D:\CodebiusBackups\Winners\postgres\2026\08\winners_2026-08-23_0300.dump`.

The filename is never the source of truth for metadata — SQLite is (`backup_runs` table). Track per backup: client, database, server, remote timestamp, download timestamp, size, hash/checksum, status, local path, method used, duration, errors.

Implementation note: the `{database}` path segment isn't a separate schema field for `fetch_existing`/`remote_dump` tasks (only `direct_dump` has a real database name, via `database_connections`), so `resolveTargetDir()` in `orchestrator/runBackupTask.ts` uses a slugified version of the task's own name instead. Revisit if that ever reads confusingly in the UI.

## Validation

A downloaded file is never automatically considered a valid backup. Minimum checks: file exists, size > 0, transfer fully completed, checksum where possible. For PostgreSQL custom-format dumps, validate with `pg_restore --list`. (Automated test-restores are a later goal, not a v1 requirement.)

Status values: `Pending`, `Running`, `Producing`, `Validating`, `Success`, `Warning`, `Failed`. (The spec originally said `Downloading` — renamed to `Producing` since it must read correctly for all three strategies, not just ones that transfer a file.)

## Retention

**Implemented** (`engine-core/src/retention/applyRetention.ts`), applied by the orchestrator after every completed attempt of every strategy — regardless of that run's own outcome (an old backup can be past policy even if today's run failed), including the `fetch_existing` no-op "already up to date" case. Configurable per client (`clients.retention_count`/`retention_days`, set via `client:create --retention-count`/`--retention-days`) with an optional per-task override (`task:create --retention-count`/`--retention-days`); neither set means no retention for that task.

Two hard invariants, enforced regardless of how aggressive the configured policy is: a run is only ever a delete candidate if a **later `Success` run with an actual file** exists (the newest is never touched), and **at least one real backup always survives**. If both `count` and `days` are configured, a run must violate *both* to be deleted (the more conservative merge, not more aggressive). Every deletion is recorded in `retention_deletions` (`retention:history <taskId>` to inspect) and is skipped on all future passes via `RetentionDeletionsRepo.listDeletedRunIds` — without that exclusion, an already-pruned run gets silently re-evaluated (and re-recorded as newly "deleted," since unlinking an already-gone file just throws ENOENT) on every subsequent run forever, which is a bug that was actually hit and fixed while building this.

**Gotcha already hit and fixed, worth knowing if you touch this code**: `RunsRepo.listSuccessfulRuns` filters to `status = 'Success' AND local_path IS NOT NULL` specifically to exclude `fetch_existing`'s no-op "no new backup needed" runs (which are legitimately `Success` but have no file). Without that filter, a no-op run — which is always the *newest* row — occupies the "never touch rank 0" protection slot while having nothing to protect, which pushed the one real backup down into "older, prunable" territory and defeated the survivor-floor invariant in testing: a single real backup got deleted, leaving zero, with several no-op Success runs sitting on top of it. If `listSuccessfulRuns` or the retention algorithm's rank/day logic changes, re-verify this exact scenario (one real Success backup, several subsequent no-op Success runs, an aggressive policy) before considering it safe.

Retention only ever considers `Success` runs "valid" — `Warning`-status backups (which do have real files) are deliberately left alone entirely, not counted and never deleted, erring conservative for files a human may not have reviewed yet. The "age" used for `retention_days` is `downloaded_at` (or the equivalent local produce time for `direct_dump`), never `remote_modified_at` — see the remote-mtime trust caveat elsewhere in this file.

## Configuration export/import

**Implemented** (`engine-core/src/config/`) — `config:export [--client <id>... | --all] [--output <file>]` and `config:import --file <path>`.

**Secrets are never exported**, by design: SSH key passphrases and DB passwords live only in Windows Credential Manager on the machine that created them, and a `secret_ref` exported to a portable file would be meaningless (or a real risk) elsewhere. Exported transports/database connections carry `hasPassphrase`/`hasPassword` booleans instead of any secret value or ref. After import, `ImportConfigResult.secretsNeedingReentry` lists (in plain language) every transport/database connection that needs its secret set again via the normal `--passphrase`/`--password` flags — this is a real, expected step in the import workflow, not an oversight.

Import **always creates new rows** — it never overwrites or merges into an existing client. A client whose name already exists fails with a clear per-client error (surfaced in that client's `errors` array) without aborting the rest of the batch; rename or remove the conflicting client first to re-import it. Within one client, transports/database connections/tasks are matched up by **name**, not by raw database id (ids are meaningless across a different SQLite file) — a task's `transportName`/`databaseConnectionName` is resolved against what was just (re-)created for that same client during the same import call.

**Bug fixed (2026-08-24)**: a task's schedule (time, enabled state, and now frequency/days-of-week/day-of-month) was exported into `ExportedTask` but **never actually restored on import** — `importOneClient()` created tasks via `createFetchExisting`/`createRemoteDump`/`createDirectDump` and simply never called `setSchedule()` afterwards, so every imported task silently came back unscheduled regardless of what the export said. Found while adding non-daily schedule frequencies (see "Scheduler" below) and fixed the same day: `importConfig.ts` now calls `deps.tasksRepo.setSchedule()` right after creating a task, if `task.scheduleTime` is set. Regression-tested (`exportImportConfig.spec.ts`) and curl/CLI-verified end-to-end with a throwaway weekly-scheduled task exported from one temp database and imported into another, confirming the restored task's schedule fields matched exactly.

**SSH private key content export/import — implemented (2026-08-24)**, closing the gap flagged earlier the same day. `ExportedTransport` gained `privateKeyContentBase64: string | null` — `exportConfig.ts` reads the key file at `transport.privateKeyPath` and base64-encodes it, leaving it `null` (graceful degradation, doesn't fail the export) if the file can't be read at export time. `importConfig.ts` writes that content to a fresh file under `paths.keysDir()` (`%PROGRAMDATA%\CodebiusBackupManager\keys\<uuid>.key` as of the 2026-08-24 secrets-storage migration below — was `importedKeysDir()`/`%APPDATA%` at the time this was first built, same day; `ImportConfigDeps.importedKeysDir` overridable for tests) and uses *that* path for the newly-created transport — `privateKeyPath` in the export is now informational only (the source machine's own path), never reused directly. When content is missing, the importer falls back to exactly today's old behavior (keeps the source path, which is almost certainly wrong on a different machine) and adds a `secretsNeedingReentry` entry telling the user to copy the file manually — reusing that existing array/reporting mechanism rather than inventing a parallel one, even though a private key file is a different kind of secret material than the passphrase/password refs it originally covered. **Security note, deliberately accepted**: this means an export file can now contain actual private key bytes (base64-embedded) for any transport whose key was readable at export time — unlike passphrases/passwords, which never leave this app's own encrypted secret storage (Windows Credential Manager at the time this was written; migrated to LocalMachine-scope DPAPI later the same day, see "Secrets storage" — the export/import boundary itself is unaffected by that migration, since it was never involved). A config export must now be handled as sensitive if any of its transports have private keys, which it wasn't before this change. Regression-tested with real temp files (`exportImportConfig.spec.ts`, `withTempDir` — content round-trips correctly, missing-file fallback still flags manual copy, `importedKeysDir` override works), and manually verified with real key files across two separate throwaway app-data directories (simulating two machines) before/after this session's automated tests — decoded content matched byte-for-byte.

## Scheduler

**v0.3.0 (2026-08-29): unattended backups now run from a dedicated Windows Service (`arkode-scheduler`), not per-task Scheduled Tasks.** The service is installed + started by the (already-elevated) NSIS installer, so there is **no per-task UAC anywhere**, and schedule edits (time/frequency/days) are pure DB writes the service picks up on its next tick. It loops every 60 s and shells out to `engine-cli scheduler:tick` — one umbrella command that runs `runDueTasks` (DB backups), the `file-task:run-due` equivalent, whatever `file-repo:run-maintenance` says is due, and stamps a `schedulerHeartbeatAt` value in `app_settings`. `isTaskDue()` / `isFileBackupTaskDue()` still decide, per tick, whether a given task's own schedule matches now — the service is just the timer.

- **The engine did not change** — `run-due`, `file-task:run-due`, `file-repo:run-maintenance`, `isTaskDue` are all unchanged; `runSchedulerTick(deps, now)` (`engine-core/src/scheduler/runSchedulerTick.ts`) composes the three with phase-level isolation (one phase throwing must not stop the next; heartbeat is written even if a phase errored — a stale heartbeat is the app's only "ticks have stopped" signal). Tested in `test/scheduler/runSchedulerTick.spec.ts`.
- **The service binary** (`packages/desktop-shell/src-tauri/src/bin/scheduler.rs`, a second `[[bin]]` in the tauri crate, ~140 lines) is deliberately thin: `windows-service` crate SCM boilerplate + a 60 s loop that `Command::spawn`s the vendored `engine-cli.exe scheduler:tick`, piping its output into `%PROGRAMDATA%\arkode\logs\scheduler-service.log`. **Implemented** (`engine-core/src/scheduler/`) — no persistent background process of our own; each task gets its own real Windows Scheduled Task.

- **Per-task schedule**: `backup_tasks.schedule_time` (24h `"HH:MM"`, validated) + `schedule_enabled`, set via `task:set-schedule <taskId> --time HH:MM` / `--disable`. Deliberately per-**task**, not one global time — a client can have multiple tasks (different databases, different strategies) that legitimately need different times; the spec's literal wording ("una hora diaria") was read as "each task gets *a* daily time," not "the whole app gets one."
- **Non-daily frequencies, added 2026-08-24** (`backup_tasks.schedule_frequency`: `'daily' | 'weekly' | 'monthly'`, plus `schedule_days_of_week` — CSV of 0=Sunday..6=Saturday, and `schedule_day_of_month` — 1-31): requested directly by the user ("que el periodo de las tareas no sea unicamente diario? por ejemplo semanal, o determinado dia"). That "no scheduled attempt yet today" condition — not the OS trigger that fired — is what actually prevents a double-run; see below.

The trade-off is that *registering* (and, discovered the same day, *querying the status of*) a SYSTEM-owned task requires the calling process itself to be running elevated (as Administrator) — a real installer already runs elevated by default, so this is a one-time cost at setup, not a per-task one, but it does mean `scheduler:install`/`scheduler:status` fail from an ordinary non-elevated terminal. `scheduledTaskStatus()` can't actually tell "not registered" apart from "registered, but you're not elevated so I can't check" — schtasks.exe gives the exact same error for both — so it separately checks elevation (`net session`) and sets `ranNonElevated: true` on a `false` result so the CLI can say "couldn't confirm," not lie and say "not registered."

## File backups (restic-backed)

**Implemented across several prior sessions, not previously documented here — this section was written 2026-08-26 to close that gap.** A fourth backup domain, parallel to the three DB-dump strategies but genuinely separate: a **file-backup task** (`local_folder` or `remote_folder`) backs up a whole folder tree via [restic](https://restic.net/) instead of producing a single dump file. Schema, CLI namespace (`file-repo:*`/`file-task:*`/`file-run:*`/`file-log:list`), repos, orchestrator, retention, scheduler, and locking are all separate from the DB-backup domain's own (`FileBackupTask`/`FileBackupRun` in `engine-core/src/fileBackup/types.ts`, not `BackupTask`/`BackupRun`) — the two domains share only `clients` and the transport table (a `remote_folder` task reuses an existing sftp/ftp transport, same as `fetch_existing`/`remote_dump` do).

- **One restic repository per client**, not per task: `file-repo:create --client <id>` initializes it at `{client.localBasePath}\_restic-repo` and prints a plaintext recovery key **once** (`file-repo:export-key` re-shows it later, but recovery must never depend solely on this machine — the key is also the repository's DPAPI-encrypted `SecretStore` value, same encryption path as every other secret in this app). Every `local_folder`/`remote_folder` task for that client backs up into the same repository as its own restic snapshot, distinguished by tag/path, not a separate repo per task — keeps restic's own dedup working across a client's related folders instead of fragmenting it.
- **`local_folder`**: `sourcePath` is a plain absolute Windows path, resolved before ever reaching restic. **`remote_folder`**: pulls from `remoteSourcePath` on an existing sftp/ftp transport first, staging into `{client.localBasePath}\_remote-staging\{taskId}\` (computed at run time, not stored — sidesteps the chicken-and-egg problem of needing the task's own id before it exists), via `remoteSync/syncRemoteFolder.ts`'s size+mtime diff (list remote tree → diff against the last local mirror state → download only new/changed files → delete locally what's gone remotely) — only *then* does restic back up the local mirror, same as it would a real `local_folder`.
- **`FileBackupRun`** mirrors `BackupRun`'s role but with restic-specific stats parsed from `restic backup --json`'s final summary line (`filesNew`/`filesChanged`/`filesUnmodified`/`filesDeleted`/`dirsNew`/`dirsChanged`/`totalFilesProcessed`/`totalBytesProcessed`/`dataAdded`/`dataAddedPacked`) instead of a single size/checksum — restic's own dedup means "data added" is usually far smaller than the source folder's total size, which is expected and not a bug.
- **Repository-level locking** (`fileBackup/locking/repositoryLock.ts`, `FileBackupOperationKind = 'backup' | 'forget' | 'prune' | 'check' | 'check_read_data'`): restic itself doesn't allow safe concurrent access to one repository, so the lock spans every task sharing it plus maintenance ops, not just one task — a second task's backup against the same repo, or a maintenance sweep, correctly waits/refuses rather than corrupting the repo. `recoverStaleRepositoryRuns` mirrors the DB domain's `recoverStaleRuns`: an in-progress row (task run or maintenance run) whose `pid` is no longer alive gets marked `Failed` so it can't block the lock forever after a crash.
- **Retention** (`fileBackup/retention/applyFileBackupRetention.ts`): restic's own `forget --keep-last <n> --keep-within <days>`, applied after every run — same count/days/both-configured-means-conservative-merge shape as the DB domain's `applyRetention.ts`, translated to restic's native policy flags instead of this app hand-computing which rows to delete.
- **Maintenance is separate and never automatic**: `prune` (reclaims space forgotten snapshots left behind) and `check`/`check_read_data` (integrity verification) are **not** run as part of a normal backup — `file-repo:run-maintenance` runs whatever's due per its own cadence (prune weekly, check monthly) or a forced `--operation`, and there's one **global** Windows Scheduled Task (`file-repo:scheduler:install-maintenance`, SYSTEM, elevated to register) that sweeps every repository, rather than a per-task schedule the way DB-backup/file-backup task schedules work — maintenance is a repository-level concern, tasks aren't.
- **restic itself is vendored**, not required to be installed on the target machine: `packages/desktop-shell/src-tauri/resources/restic/restic.exe`, resolved at dev time via `RESTIC_PATH` (same pattern as `PG_DUMP_PATH`/etc.) and cached under `packages/desktop-shell/.build-cache/` during packaging.
- **UI**: originally file-backup tasks lived *only* in the per-client ficha's "Archivos" tab (`FileBackupsPanel.tsx`) and were deliberately kept off the Dashboard / global Tareas / Historial. **That separation was reversed 2026-08-29 — see "Unified DB + file backup tasks in the UI" below.** File-backup tasks now appear alongside DB-backup tasks everywhere tasks/runs are listed (a `KindBadge` tells them apart), the ficha's old "Archivos" tab was renamed **"Repositorio"** and slimmed to just the restic-repo concerns (path, recovery key, prune/check, snapshot browser + restore/delete), and file-backup tasks gained the same in-app "Registrar en Windows" scheduler button DB tasks have.

**Live end-to-end verification of `remote_folder` (SFTP + FTP), 2026-08-26, and a real bug found and fixed along the way.** Both transports were exercised against real servers, not mocks: Windows OpenSSH Server already on this dev machine for SFTP (working around a real Windows quirk — accounts in the local Administrators group have `~/.ssh/authorized_keys` ignored entirely by sshd in favor of `C:\ProgramData\ssh\administrators_authorized_keys`, which needs elevation + strict ACLs via `icacls` to write; confirmed SFTP's absolute-path convention on Windows OpenSSH is `/C:/Users/...`, leading slash + drive letter + colon, by hand via the `sftp` CLI), and a throwaway local `ftp-srv`-based FTP server for FTP, cleanly torn down afterward.

- **Real bug found: `ftpAdapter.ts`'s `listRemoteTreeRecursive` used `entry.modifiedAt ?? new Date()` as its fallback** whenever `basic-ftp` couldn't parse the server's LIST timestamp — confirmed via `ftp-srv`, whose classic Unix LIST format omits the year, that this fallback fires routinely, not just on some edge-case server. `new Date()` as a fallback is actively destructive here: it produces a *different* timestamp on every single listing, which defeats `syncRemoteFolder`'s whole size+mtime diff — every file looks "changed" on every run, forever, against any server without MLSD support.
- **Fixed**: the fallback is now a fixed epoch (`new Date(0)`), stable across listings, so the diff correctly falls back to size-only comparison instead (the same accepted limit the mtime+size heuristic already carries elsewhere — it only misses the rare same-size-different-content edge case).
- **Verified before and after, against the real live FTP server**: before the fix, steady-state (no real changes) incorrectly showed all 4 test files "changed" on every run; after, steady-state correctly showed 0 changed, and a real mutation test (1 new file, 1 changed, 2 unmodified, 1 deleted) produced the exact correct diff.

## Manual backup deletion

**Implemented 2026-08-26**, for both domains — a deliberate human action to delete one specific backup, distinct from automated retention (see "Retention" above and the file-backup domain's own retention note above). The key design difference: a manual delete is **allowed to override** retention's own "never delete the newest / never leave zero" guardrails — protected only by a strong confirmation dialog in the UI, not a hard block, matching this app's existing "never un-overridable by the person running it" precedent (e.g. `--force` on the direct_dump compatibility gate).

- **DB dumps** (`retention/deleteBackupRun.ts`, `run:delete <runId>` / `POST /runs/:id/delete`): deletes the file at `backup_runs.local_path` (swallowing `ENOENT` — already-missing is not an error), records the deletion in the existing `retention_deletions` table with `reason: 'manual_delete'` (that column was already unconstrained `TEXT`, no schema change needed), and **deliberately leaves the `backup_runs` row itself untouched** — same behavior automated retention already has, and `GET /runs/:id/download` already treats "row says there's a file, but it's missing on disk" as the normal signal for a pruned run, so nothing downstream needed to change. Rejects an in-progress run and a run with no local file with a clear error; unlike retention's own loop (log-and-skip), this throws straight through — it's one explicit user action, the caller should see a real failure.
- **File-backup snapshots** (`fileBackup/retention/deleteFileBackupRun.ts`, `file-run:delete <runId>` / `POST /file-runs/:id/delete`): restic's own `forget` is policy-based only (`--keep-last`/`--keep-within`, always unions a `--keep-last 1` survivor floor) and **cannot target one specific snapshot** — `resticClient.ts` gained `forgetSnapshot(repoPath, password, snapshotId)`, restic's positional-ID form (`restic forget <snapshotId>`, no `--keep-*` flags), which — unlike the policy form — genuinely can remove the last remaining snapshot if that's explicitly what's requested. Acquires the same repository-level lock (`'forget'` operation kind) described above. Records into `file_backup_retention_deletions` with `reason: 'manual_delete'`, leaves `file_backup_runs` untouched. **Deletion is cheap/immediate (metadata-only) but does not reclaim disk space** — that only happens on the next `prune`, a separate deliberately-manual/scheduled operation — this nuance is surfaced directly in the UI's confirmation text so it's never a silent surprise.
- **UI**: a `TrashIcon` `IconButton` (`tone="danger"`) next to the existing download/restore actions in `Historial.tsx`, `ClienteDetalle.tsx`'s Backups tab (DB runs), and `FileBackupsPanel.tsx`'s snapshots table (file-backup runs) — each behind a `window.confirm()` whose copy states the real consequence (irreversible for DB dumps; "space frees up on the next prune" for snapshots).
- **Verified end-to-end for real against a throwaway `CODEBIUS_APP_DATA_DIR`, both domains, through the actual CLI/HTTP surface (not just the underlying engine-core functions, which already had unit coverage)**: for file backups, ran a real `local_folder` task twice against a real vendored restic repository (two real snapshots), deleted the first via `file-run:delete`, and confirmed via `restic snapshots` that only the second remained and via `restic check --read-data-subset=1/1` that the repository was still fully intact (zero errors, same pack count — confirming disk usage is genuinely unchanged until a prune) — and confirmed `file_backup_runs`' row for the deleted snapshot was untouched. For DB dumps, seeded a real `Success` run (via the real `RunsRepo` API, pointing at a real file on disk) and ran the actual `run:delete` CLI command against it, confirming the file was gone from disk afterward while the run row (status, `localPath`, size, checksum) stayed exactly as it was.

### Stale-run recovery bug — a recycled PID kept a run stuck forever (fixed 2026-08-29)

Found via a real production incident: the user's `Uploads matexmate` file-backup run (first full FTP sync of `/home2/matexmate/public/uploads`) was interrupted when its process died, and then **never** got marked `Failed` — it sat at `Producing` ("Generando" in the UI) for a day, holding the repository lock, and neither reopening the app nor "Check ahora" cleared it. `snapshot_id` was `null`, so it had died during the FTP sync phase (no restic snapshot, no stale restic lock — the repo itself was clean); the stuck row was cleared with a one-off `UPDATE file_backup_runs SET status='Failed' WHERE status IN ('Running','Producing','Validating')`.

Root cause: both domains' stale-run recovery (`recoverStaleRuns` in `orchestrator/runBackupTask.ts`, `recoverStaleRepositoryRuns` in `fileBackup/locking/repositoryLock.ts`) decided "is this run's owner still alive?" with a bare `process.kill(pid, 0)` — which returns true for **any** PID currently in use, regardless of which process holds it. Windows recycles PIDs fast, so a crashed run's stored PID is routinely "alive" again as some unrelated program → recovery skips it → the run (and its lock) is stuck permanently. The `isProcessAlive` helper was duplicated in both places, so both had the bug.

Fix: new `src/util/processIdentity.ts` (domain-neutral, imported by both — the file-backup domain's "don't reach into tested DB-backup code" rule is about not importing the *orchestrator's internals*, not a shared low-level OS util) with `isStaleInProgressRun({ pid, startedAt }, deps?)`:
- No PID, or PID not in use → stale (fast path, unchanged).
- PID in use, row younger than `IN_PROGRESS_SCRUTINY_AFTER_MS` (30 min) → **trusted, no OS call** — the overwhelmingly common healthy "a run really is running right now" case pays nothing.
- PID in use, row older → query the PID holder's start time (`Get-CimInstance Win32_Process`, Windows-only, 5s timeout, null on any failure). If the holder started *after* the run row was written it cannot be the process that wrote the row → recycled PID → stale.
- Holder start time unknowable → keep, unless the row is older than `MAX_IN_PROGRESS_RUN_MS` (24 h) → reclaim regardless (a run that genuinely ran 24 h is pathological and worth failing). This 24 h ceiling only ever reclaims when the PID's identity *couldn't* be verified, so it can't race a genuinely-running process into a double-run.

Both `recoverStaleRuns`/`recoverStaleRepositoryRuns` and the `checkRepositoryLock` / `runBackupTask` "still in progress?" filters now use `isStaleInProgressRun`. `fileBackup/util/isProcessAlive.ts` deleted (its only caller was `repositoryLock.ts`). New `test/util/processIdentity.spec.ts` (7 tests, all deps injected — no real PowerShell in the suite); the existing `runBackupTask.spec.ts` stale-run tests (`pid: process.pid` = alive+recent → trusted; `pid: 999999` = dead → reclaimed) still pass unchanged.

## Off-site replication to Google Drive (rclone)

**Started 2026-08-30, planned + Phase A/B code landed the same session; NOT yet live-verified against a real Google account.** An **opt-in** copy layer that mirrors a client's backups to Google Drive *after* a backup finishes — it never touches the proven backup orchestrators (`runBackupTask.ts`, `runFileBackupTask.ts`) or the restic engine. Answers "there's no 3-2-1 copy — if the local disk dies, the recovery key alone is useless." Chosen via AskUserQuestion: **both** restic repos and DB dumps; `rclone sync` (byte-for-byte mirror, not `restic copy`); Google **personal** account via rclone's OAuth (refresh token auto-renews); cadence = **after every successful backup + retry on the next service tick**; **per (client, content) granularity** — each target has its *own* Google account + folder, no global/shared Drive config; and **nothing is forced** — solo dumps, solo archivos, ambos, or ninguno.

- **rclone is vendored** (`prepare-rclone.mjs` → `resources/rclone/rclone.exe`, MIT, ~50MB extracted, `RCLONE_PATH` + `toolPaths.ts` `'rclone.exe'` entry, `lib.rs` sidecar env, `tauri.conf.json` `beforeBuildCommand`/`bundle.resources`, `release.yml` cache step, `LICENSES/NOTICE.md`). restic itself has no Drive backend; rclone is its documented bridge.
- **Schema** (`0015_add_replication_targets.sql`, two plain new tables, no rebuild): `replication_targets` (`UNIQUE(client_id, content)`, `content` ∈ `restic_repo | db_dumps`, own `rclone_config_secret_ref` + `remote_path` + `encrypt_with_crypt`/`crypt_password_secret_ref` + `enabled` + `last_replicated_at`/`last_status`/`last_error`) and `replication_runs` (status state machine + `pid` for recycled-PID-safe stale recovery). Repos: `db/repositories/replication{Targets,Runs}Repo.ts`.
- **Encryption asymmetry, deliberate**: a restic repo is already encrypted at rest → `restic_repo` targets `rclone sync` raw ciphertext (Google sees only ciphertext; the recovery key never leaves the machine). DB dumps are plaintext at rest → `db_dumps` targets default to wrapping the upload in an rclone **`crypt`** remote with their *own* generated password (shown once, re-viewable, flagged as "save it outside this PC, not in a config export" — same treatment as the restic recovery key). `--no-encrypt` opts out.
- **`replication/` module** (top-level, spans both domains): `rcloneClient.ts` (the only place that knows the rclone CLI — `sync`/`about`/`copyDown`/`obscure`/`authorizeDrive`/`withRcloneConfig` writing a locked-down temp `rclone.conf` deleted in `finally`); `rcloneConfig.ts` (pure `.conf` INI builder — `[drive]` always, `[gdrive-crypt]` wrapping `drive:` when encrypted); `replicateTarget.ts` (resolve source → decrypt config → take the repo lock via the new `'replicate'` `FileBackupOperationKind` (restic_repo, and db_dumps when the client also has a repo) → pre-flight (`restic snapshots` readability / dir-exists) → `rclone sync … --backup-dir <remote>:arkode/_trash/<runId>` → record a `replication_runs` row + `last_*`; ordinary failures fold into the row, never a throw; `preflightOverride`/`rcloneOverride` are test-only seams); `replicationDue.ts` (`isReplicationDue` — enabled AND (never replicated | last failed | a `Success/Warning` backup for the client finished after `last_replicated_at`), with a 5-min interval floor; **derived from existing run rows — no `dirty` flag, no orchestrator write hook**); `runDueReplications.ts` (per-target isolation).
- **Scheduler**: `runSchedulerTick` gained a **4th phase** after maintenance (so it captures that tick's fresh snapshots + prune), phase-isolated, heartbeat still always stamped. `RunSchedulerTickDeps.replicationTargetsRepo`/`replicationDeps` are **optional** — absent (or zero targets) ⇒ the phase is a zero-cost no-op and no existing backup changes behaviour. `SchedulerTickResult` gained `replication`.
- **CLI**: `replication:add|authorize|paste-token|list|test|run|enable|disable|remove|runs|pull`. `authorize` runs `rclone authorize "drive"` (opens the browser, blocks); `paste-token` is the headless-server fallback. `pull` is disaster recovery (`rclone copy` the remote copy down → then `restic -r <dir>` restore normally for restic_repo).
- **serve**: `GET/POST /replication-targets`, `POST /replication-targets/:id/{authorize,test,run,pull}`, `GET /replication-targets/:id/crypt-password`, `PATCH /replication-targets/:id`, `POST /replication-targets/:id/remove`, `GET /replication-runs`. Test/run return `502` on a failed outcome (request itself succeeded), matching the existing `test-connection` convention.
- **Tauri**: `rclone_authorize_drive` command (runs the vendored `rclone authorize "drive"`, returns the token JSON to the UI, which POSTs it to `/…/authorize`). No new capability permission — it's a `generate_handler!` command, not a plugin API.

  - **A second, separate bug, found 2026-08-25 (v0.1.14)**: reported directly ("cuando abro un modal, no puedo mover la ventana ni clickear los botones de la barra de arriba"). Cause this time wasn't permissions — `TitleBar.tsx` had no `position`/`z-index` of its own, a plain static-flow element, while `Modal.tsx`/`SshSetupGuide.tsx`'s overlays are `fixed inset-0 z-50`. Per normal CSS stacking rules, a positioned element with an explicit z-index always paints (and hit-tests) above a non-positioned sibling regardless of DOM order — so any open modal's full-viewport overlay silently sat on top of the title bar the whole time, swallowing both the drag region and the three window-control buttons' clicks. **Fixed** with `relative z-60` on `TitleBar.tsx`'s root div (higher than every modal's `z-50`) — it now always paints above any modal, keeping the window draggable and its buttons clickable regardless of what's open. Same class of bug as the permissions one above (only surfaces with real mouse interaction, which screenshots and Claude's own no-input-injection limitation can't catch) — worth deliberately testing "does X still work with a modal open" for any future title-bar-adjacent change, not just at rest.

## Error handling

- A failure for one client must never stop backups for other clients — tasks are independent.
- Never silently delete partial downloads: write to a temp extension (e.g. `.part`) and rename only after transfer *and* validation succeed.
- The app must be able to recover cleanly from an interrupted run.

## Logging

Every run logs: start, connection, remote generation (if applicable), download, validation, retention application, result, duration, and the full error message on failure. Logs must exist as files in addition to SQLite records, so diagnosis is possible even if the app/DB itself is having problems.

**`prepare-pg-tools.mjs`'s `tar` extraction bug — three rounds, root-caused each time, ultimately fixed by dropping `tar` entirely.** The EDB zip download itself was already confirmed genuinely complete and correct on the runner (HTTP 200, exact expected byte count — the earlier "EDB might be blocking datacenter IPs" theory was wrong, disproven by the same hardening that was built to catch it), but extraction kept failing on the GitHub-hosted runner specifically, never on this dev machine, through three distinct causes:
1. `--strip-components=1: Not found in archive`. Root cause: `tar` resolves to two genuinely different implementations depending on the shell. Every local test on this dev machine runs through Git Bash, whose own bundled `tar` is real GNU tar — which accepts `--strip-components` in any position on the command line. The GitHub Actions runner invokes this script through PowerShell, which instead resolves Windows' own bundled `tar.exe` (libarchive/bsdtar) — and bsdtar requires `--strip-components` (and other options) to appear *before* the file-operand list, silently misbehaving otherwise. Reproduced directly against this machine's real `System32\tar.exe`: the old argument order failed with the identical error extracting a real downloaded MariaDB zip, and moving `--strip-components` before `-xf` fixed it immediately.
2. After reordering, GNU tar (Git Bash, used for that same local reproduction) separately turned out to misparse a bare `C:\...` destination path as `host:path` remote-tar syntax ("Cannot connect to C: resolve failed") — fixed locally with `--force-local`.
3. That `--force-local` fix then broke the *next* real CI run (`v0.1.7`) with `Option --force-local is not supported` — this GitHub-hosted runner's specific bsdtar build doesn't have that flag compiled in at all, even though this dev machine's `System32\tar.exe` does.

Three genuinely different `tar` behaviors in one day was the signal to stop patching flags and drop the dependency on system `tar` entirely for this script — switched to the same `extract-zip` npm package `databaseConnections/downloadTool.ts` already uses for its own runtime extraction (see the "direct_dump tool version management" auto-download note below), which behaves identically regardless of the host environment. **Confirmed fully fixed, not just theorized**: `v0.1.8` (a no-functional-change version bump published purely to verify this) ran the complete release pipeline end-to-end on a real GitHub-hosted runner — tests, signed build, `latest.json`, and a real published GitHub Release — with zero manual intervention, the first time this pipeline has ever fully succeeded. **This was never actually CI-only**, worth remembering if it ever comes up again: any real manual build run from a plain PowerShell terminal instead of Git Bash would have hit the same class of failure on this dev machine too; every real release through v0.1.6 simply happened to always go through Git-Bash-resolved GNU tar.

## UX direction

Desktop-first only (no mobile/responsive requirement), dark mode, dense/information-first layout. The dashboard's single job is answering, in about five seconds: **do all clients have a recent, valid backup?** Problems must stand out far more visually than healthy backups.

Avoid: giant cards, decorative gradients, charts without real utility, unnecessary animation, excessive modal usage. This is an internal technical tool, not a marketing surface.

V1 screens: Dashboard, Clientes, Detalle de cliente, Conexiones, Tareas de backup, Historial, Logs, Configuración. Per-client actions: run backup now, test connection, view backups, open local folder, view last error.
